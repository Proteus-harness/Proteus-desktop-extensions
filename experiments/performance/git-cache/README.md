# Память истории Git при закрытых preview

Стенд запускает **готовое** расширение Git по протоколу 4. Он не запускает
Desktop, Core, модель или настоящий репозиторий и ничего не собирает.
Loopback HTTP отвечает только синтетическими commit/diff DTO. Сэмплер считает
дерево процесса расширения; Python-сервер и драйвер в RSS/PSS не входят.

```sh
python3 experiments/performance/git-cache/bench.py \
  --package ../Proteus-desktop/build/Proteus/share/extensions/git \
  --output target/verification/git-cache-before
```

Сценарий по умолчанию: badge сохраняет сессию, последовательно открываются
48 разных коммитов с общим patch и выбранным файловым patch по 384 КиБ.
Каждый preview закрывается. Каждые восемь коммитов записываются RSS, PSS,
VmHWM, CPU и HTTP-счётчики. Драйвер читает и сразу выбрасывает большие roots,
не накапливает историю ответов; stdout-reader общий с renderer benchmark.

После последнего preview отдельно измеряется состояние с одним badge.
Затем закрываются badge и context, и тот же последний commit открывается
заново: новый `/workspace/commit` подтверждает удаление владельца кеша.
`close_context` следует посылать **после** закрытия его поверхностей — SDK
оставляет живой context, пока в нём есть хотя бы один вид.

В `report.json` записаны SHA-256 бинарника, манифеста, стенда, общего Process
helper и sampler, параметры входа, точки замера, итоговые HTTP-счётчики и
наблюдаемый пик. `samples.jsonl` содержит непрерывные выборки. Большие roots
в `protocol.jsonl` редактируются общим helper; содержимое не сохраняется.

Для сравнения before/after запускайте варианты **последовательно**, на одном
входе, без параллельных сборок, GUI и других benchmark. Передавайте целую
готовую папку пакета, а не только бинарник. Создавайте новую выходную папку
для каждого запуска. Это тёплый OS cache и синтетический сценарий; его нельзя
обобщать на память всего приложения или реальные рабочие проекты.

Логический предел immutable history cache — **16 записей / 8 МиБ** суммарно
для commit и файловых diff. Это примерно восемь соседних пар commit+file,
а byte limit ограничивает большие patch и сообщения независимо от их числа.
Full/short aliases принадлежат одной записи и удаляются вместе. Учитываются
UTF-8 bytes JSON тем же `serde_json` serializer без создания второй полной
строки, плюс bytes строк ключа/aliases. Превышающий лимит ответ показывается,
но не удерживается в кеше и не вытесняет небольшие полезные записи.

Лимит JSON bytes не равен размеру Rust heap или RSS: serde-дерево, активные
виды и allocator имеют отдельную стоимость. `VmHWM` — максимум процесса,
он не уменьшается после освобождения. Сохранение RSS после close само по
себе не доказывает утечку: проверяйте повторный HTTP, logical bound в тестах,
стабилизацию нескольких точек и освобождение последнего владельца отдельно.

Проверки:

```sh
cargo test --locked -p extension-git
python3 -m unittest discover -s experiments/performance/git-cache -p 'test_*.py'
```
