# Работа С Proteus-desktop-extensions

Поставляемые по умолчанию процессные расширения приложения Proteus.
Автор набора — Proteus Project. Формат и границы описаны в PROTOCOL.md.
Документация — на русском языке.

packages/<id> — Rust-бинарник с манифестом; sdk — общий крейт
proteus-extension. package.py собирает release-бинарники и кладёт их с файлом
лицензии пакета в каждый самостоятельный ZIP или portable пакет. Общие помощники держите в SDK,
а не копиями в пакетах; не добавляйте сторонние зависимости без конкретной
необходимости. shelved/ — отложенные Python-пакеты со старым SDK, не поставляются. Включённое по умолчанию расширение использует тот
же контракт, что и установленное пользователем.

Не переносите поведение конкретного пакета в GPUI-клиент и не вводите ветки по
id. Для нового нативного виджета измените публичную схему клиента и все
потребители вместе. Черновой протокол не требует legacy aliases.
При смене сессии отбрасывайте устаревшие ответы, сохраняйте action sequence,
фокус, клавиатуру и отсутствие повторной передачи текста по каждому delta.
Не записывайте токены сервера или содержимое реальных сессий в логи.

Для правки одного пакета используйте `cargo test --locked -p extension-ID` и
`python3 package.py --package ID` (ZIP) или `--package ID --dev` (локальный
бинарник). Остальные пакеты и приложение для этого не пересобирайте.
Общие изменения SDK/протокола и упаковщика проверяйте через
`cargo test --workspace` и `python3 -m unittest discover -s tests -p 'test_*.py'`.
При изменении общего контракта — ещё `python3 scripts/test.py --build-extensions`
и живое окно в Proteus-desktop (соседний ../Proteus-desktop). Для повторной
wire-проверки уже готовых расширений используйте `--extensions`; обычный
Desktop `scripts/test.py` не собирает расширения и не включает эту проверку.
Тесты используют синтетические данные и loopback HTTP.

После проверенной production-правки создайте commit. Для обновления набора в
portable запустите из Proteus-desktop
`python3 scripts/portable.py --components extensions --no-archive`;
для изменения общего протокола — `--components desktop extensions`.
Остальные компоненты берутся целиком из готового `build/Proteus` или `--base PATH`.
Установку одного ZIP проверяйте без пересборки Core/Desktop. `--reuse-binaries`
копирует готовую базу целиком и не обновляет расширения из исходников.
`--full` нужен только для явно выбранного bootstrap/полной поставки;
`--fast` и `--reuse-hosts` удалены. Подробности — в
[BUILDING.md клиента](../Proteus-desktop/BUILDING.md).

Правки документации и сборочных скриптов проверяйте целевыми Python-тестами,
ссылками и `git diff --check`; не запускайте Cargo или portable только ради
такой проверки. Для UI используйте готовые синтетические чаты или готовый
seeder; не компилируйте Core ради получения тестовых чатов.

## Стоимость Renderer И Cache

- Считайте стоимость по изменившемуся source/settings, не по числу читателей.
  Передавайте immutable данные borrow/move, а копию оставляйте там, где
  snapshot должен жить независимо от исходного владельца.
  При разборе уже принадлежащего SDK сообщения переносите большие поля в
  retained view без глубокого clone; сохраняйте порядок validation, прежний
  payload при отказе и освобождение данных при close/смене поверхности.
- Cache имеет явный ключ, предел entries/bytes, eviction и освобождение
  владельцев при closed/смене source. Ключ покрывает все влияющие на output
  source, theme и settings; нормализация ключа не должна обходить прежнюю
  validation, request-size limit или менять порядок ошибок.
- Для учёта JSON bytes используйте тот же serializer/escaping, что для wire,
  но не создавайте полную строку только ради len. Считайте UTF-8 bytes, не
  символы; overflow и serialization error не должны пропускать byte limit.
  Это логическая граница encoded payload, не точное измерение RSS.
- Cache miss, hit, смена темы/настроек, closed и превышение лимита проверяйте
  в существующем package test target. Экспериментальный renderer не становится
  частью стандартной поставки из-за общего helper.

Устранённая allocation — source evidence; утверждение о latency/RSS/CPU
требует сопоставимого замера с revisions, размерами входа и cold/warm режимом.

## Zed Как Образец

Файлы, git и другие панели повторяют Zed (~/Code/zed,
github.com/zed-industries/zed): поведение, раскладку, тексты, меню и клавиши.
Своё не придумывайте; не хватает виджета — добавьте его в публичную схему
клиента по образцу Zed. Образец — исходники Zed, а не догадки по скриншоту:
возьмите из кода этого места в ~/Code/zed идею, стиль и расположение; копировать
построчно не нужно. Код Zed можно переносить; в начале такого файла
укажите источник: `// Адаптировано из Zed: crates/<путь>`.

Единый стиль: правила вида и поведения — в DESIGN.md клиента
(../Client/DESIGN.md в общем workspace, ../Proteus-desktop/DESIGN.md при
отдельных checkout), они действуют и для пакетов. Пакеты собирают интерфейс только из примитивов схемы
клиента и не подменяют их своими (текстовые шевроны, «…» в обрезанном тексте,
самодельные таблицы и цвета). Одна и та же вещь — список изменений, дерево,
история, diff — выглядит одинаково во всех пакетах. Нужен новый вид — добавьте
общий примитив в клиент по образцу Zed и переведите на него все пакеты.

Лицензии как в Zed: в корне LICENSE-GPL и LICENSE-APACHE, у каждого крейта
поле `license` и symlink на файл корня. Пакеты в packages/ — GPL-3.0-or-later,
SDK (sdk/, крейт proteus-extension) — Apache-2.0, чтобы сторонние расширения
могли выбирать лицензию сами. В SDK нельзя переносить код GPL-крейтов Zed.
Проверка: `python3 ../Proteus-desktop/scripts/check_licenses.py .`.
